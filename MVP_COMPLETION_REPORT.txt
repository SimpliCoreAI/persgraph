================================================================================
                           TOOL/SCOPE BOUNDARIES
================================================================================

Purpose: Prevent tool leakage between workers, enable runtime enforcement

Example Boundary Violations (Prevented):
  ✓ InboxTriageWorker cannot use chroma, llm, or ollama
  ✓ IngestWorker cannot write to places_db or calendar_db
  ✓ DebriefWorker cannot call url_fetcher (read-only)
  ✓ CalendarPrepWorker cannot access travel tools
  ✓ TravelScoutWorker cannot ingest URLs (not its role)

Enforcement Mechanism:
  1. Declarative: Capabilities defined in worker_registry.py
  2. Runtime: validate_worker_access() can be called before operations
  3. Future: Middleware can intercept tool access

Benefits:
  • Credential isolation (API keys limited to scoped workers)
  • Resource contention prevention (no DB monopolies)
  • Blast radius containment (errors don't corrupt shared state)
  • Clear responsibility boundaries (worker + tool alignment)

================================================================================
                          ROUTING ARCHITECTURE
================================================================================

Flow Diagram:
  
  User Input
      ↓
  orchestrator.run_with_routing(raw_input, sender_id)
      ↓
  route_command(raw_input, user_context)
      ├─ Parse command + args
      ├─ Lookup WorkerType in get_worker_for_command()
      ├─ Build RoutedTask(worker_type, payload, user_context)
      └─ Return RoutedTask
      ↓
  [RoutedTask] 
      │
      ├─ If worker_type is set:
      │  └─ Instantiate Worker(worker_type)
      │     └─ worker.run(routed_task)
      │        └─ worker.execute(payload)
      │           └─ Return result (string)
      │
      └─ If worker_type is None:
         └─ Bypass to command_handler (orchestrator dispatch)
            └─ Return result (string)
      ↓
  Result (returned to user)

MVP vs. Future:
  MVP:    Workers delegate to command_handler (thin wrapper)
  Future: Workers spawn as separate processes, use message queues

================================================================================
                          HOW TO USE THE ROUTING LAYER
================================================================================

Pattern 1: Route a Command
  from agents.orchestrator.router import route_command
  
  routed = route_command("/note buy groceries", user_context={"tier": "user"})
  print(routed.worker_type)  # WorkerType.INBOX_TRIAGE
  print(routed.command)      # "/note"
  print(routed.args)         # "buy groceries"

Pattern 2: Validate Capabilities
  from agents.orchestrator.router import validate_worker_access
  from agents.orchestrator.worker_registry import WorkerType
  
  ok, denied = validate_worker_access(WorkerType.INBOX_TRIAGE, ["places_db", "llm"])
  if not ok:
      print(f"Worker denied: {denied}")  # ['llm']

Pattern 3: Introspection
  from agents.orchestrator.orchestrator import describe_routing
  
  routing = describe_routing()
  print(routing["routing_table"])  # All command→worker mappings
  print(routing["workers"])        # All worker capabilities

Pattern 4: Debug Routing
  ROUTING_DEBUG=1 python3 -c "from agents.orchestrator.router import route_command; \
  r = route_command('/note test'); print(r)"
  # Outputs: RoutedTask(worker_type=<WorkerType.INBOX_TRIAGE: 'inbox_triage'>, ...)
